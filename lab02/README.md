# Лабораторная работа №2

## Тема

Влияние system prompt, temperature и max_tokens на ответы локальной LLM при разборе событий информационной безопасности.

## Цель

Выяснить, какие параметры запроса реально меняют форму и полноту ответа, а какие на данной модели и сервере ведут себя неожиданно (в том числе обрезка и «пустой» ответ при малом лимите токенов).

## Задачи

1. Зафиксировать baseline: один и тот же инцидент без явных параметров генерации.
2. Сравнить три system prompt на одном user prompt.
3. Измерить разнообразие ответов при temperature 0.0 / 0.3 / 0.7 / 1.0 (по 5 повторов).
4. Проверить лимиты `max_tokens` 80 / 300 / 900 на объяснении архитектуры RAG.
5. Сохранить полные ответы (JSONL) и сводную таблицу (CSV).

## Используемые технологии

- Python 3, `openai`, `python-dotenv`
- LM Studio, `http://localhost:1234/v1`
- Модель: `google/gemma-4-e4b` (локально)
- Параметры, которые явно задавались в этапах 3–4: `temperature`, `max_tokens`

Этап 1 и 2 не передают temperature/top_p/max_tokens в API специально: иначе нельзя отделить «поведение по умолчанию» от наших настроек.

## Описание решения

### Этап 1. Baseline

Запрос: 25 неудачных входов в `admin` в 03:17, затем успешный вход с того же IP. Три повтора без параметров. Так видно, насколько модель и так «размазывает» инцидент в длинный текст, ещё до смены промпта.

### Этап 2. System prompt

Три роли на том же user prompt:

- `sys_01` — «отвечай на запрос»;
- `sys_02` — не больше пяти пунктов, у каждого риск и действие;
- `sys_03` — факты / гипотезы / действия, не выдумывать недостающее.

Меняется только system, чтобы разница не списывалась на другой вопрос.

### Этап 3. Temperature

Промпт про пять названий SOC-сервиса, по 5 повторов на значение. Один запрос на temperature ничего не доказывает: нужен набор, чтобы отличить случайность от эффекта параметра.

### Этап 4. max_tokens

Один объясняющий промпт (RAG) и три лимита. Ошибки API не роняют весь прогон: `ask_model` пишет их в поле `error`. Для Gemma через LM Studio `temperature` и `max_tokens` принимаются, но лимит токенов ведёт себя не как «напиши короче», а как жёсткая обрезка (и иногда как расход бюджета на служебные токены).

Логи: JSONL — полный текст, CSV — превью для таблиц.

## Эксперименты и результаты

Модель во всех строках: `google/gemma-4-e4b`. Сырые данные: [results/results.csv](./results/results.csv), полные ответы — [results/results.jsonl](./results/results.jsonl).

### Этап 1. Baseline

| Повтор | Задержка, с | Токены ответа | Наблюдение |
|---:|---:|---:|---|
| 1 | 265 | 1907 | Длинный разбор brute-force без запрошенной структуры |
| 2 | 235 | 1929 | Снова эссе, термины Brute Force / dictionary attack |
| 3 | 140 | 1323 | Тот же вывод, чуть короче |

Без system prompt модель не отделяет факты от гипотез и тратит сотни токенов на вступления. Средняя задержка этапа — около 213 с.

### Этап 2. System prompt

| system_id | Задержка, с | Что изменилось |
|---|---:|---|
| sys_01 | 244 | Снова длинный свободный текст, как baseline |
| sys_02 | 117 | Появились пункты с риском и действием, ответ заметно короче |
| sys_03 | 162 | Явные блоки «Факты / Гипотезы / Действия» |

Вывод этапа: форма ответа определяется system prompt сильнее, чем формулировка инцидента. Для SOC-сценария нейтральный prompt бесполезен — модель не экономит токены сама.

### Этап 3. Temperature

Пять повторов, уникальность считалась по полному тексту ответа в JSONL.

| temperature | Уникальных из 5 | Средняя задержка, с | Наблюдение |
|---:|---:|---:|---|
| 0.0 | 2 | ~82 | Почти одни и те же названия (SentinelLogix), но не 1 из 5: детерминизм неполный |
| 0.3 | 5 | ~87 | Все ответы разные, ещё узнаваемый стиль |
| 0.7 | 5 | ~85 | Сильный разброс имён (AegisView, Chronosight, …) |
| 1.0 | 5 | ~58 | Разброс плюс нестабильная длина (один ответ оборвался за 22 с / 251 токен) |

Temperature 0 на этой связке LM Studio + Gemma не даёт полного повтора. Для «креативных» названий 0.3 уже даёт пять разных вариантов; для аналитики инцидента разумнее держать значение ближе к 0, чем к 1.

### Этап 4. max_tokens

| max_tokens | completion_tokens | Длина текста | Что произошло |
|---:|---:|---:|---|
| 80 | 80 | 0 символов | Бюджет исчерпан, в `message.content` пустая строка |
| 300 | 300 | 503 символа | Обрезка на вступлении про RAG, этапы ingestion/chunking не раскрыты |
| 900 | 900 | 24 символа | Текст «Привет! Отличный вопрос.» при 900 completion-токенах |

Лимит 80 на объясняющий промпт непригоден: ответ фактически пустой. Лимит 300 обрезает содержание. Случай 900 показывает, что счётчик токенов и видимый текст могут расходиться (часть бюджета, судя по объёму usage, уходит не в итоговый `content`). Для отчёта по RAG нужен либо больший лимит, либо отдельная проверка, не считает ли сервер reasoning/служебные токены в `completion_tokens`.

## Вывод

System prompt — самый дешёвый способ получить пригодный для SOC формат: те же факты инцидента, но пункты «риск / действие» вместо эссе. Temperature на Gemma через LM Studio повышает разнообразие уже с 0.3; ноль не гарантирует идентичные ответы. `max_tokens` здесь не «сделай короче», а «обрежь»: малый лимит даёт пустой или куцый текст, большой не гарантирует, что видимый ответ заполнен содержательно.

Рабочая конфигурация для разбора логов по итогам прогона: структурированный system prompt (как `sys_03`), temperature около 0–0.3, `max_tokens` заметно выше 300 и контроль, что в CSV/JSONL есть непустой `answer`.
