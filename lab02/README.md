# Лабораторная работа №2

## Тема

Параметры генерации и конфигурация больших языковых моделей



Цель

Научиться управлять поведением LLM с помощью параметров генерации и системных инструкций, а также экспериментально выбирать конфигурацию модели под конкретную прикладную задачу.

Задачи

1. Зафиксировать базовое поведение модели при параметрах по умолчанию
(baseline).
2. Сравнить ответы модели на один и тот же запрос при трёх разных
system-промптах.
3. Проверить, как меняется разнообразие ответов при temperature = 0.0,
0.3, 0.7, 1.0 (по 5 повторов на каждое значение).
4. Проверить, как ограничение `max\_tokens` (80 / 300 / 900) влияет на
полноту и структуру ответа.
5. Свести результаты всех этапов в таблицы и сделать выводы.

## Используемые технологии

* Python 3.x
* библиотека `openai` (OpenAI-совместимый клиент)
* `python-dotenv` для чтения `.env`
* LM Studio — локальный сервер с моделью по OpenAI-совместимому API

Модель: задаётся через `LLM\_MODEL` в `.env` (в коде указано значение по
умолчанию `google/gemma-4-e4b` — это дефолт, реальная модель — та, что
загружена в LM Studio на момент прогона).
Запуск: локальный, через LM Studio (`http://localhost:1234/v1`).

## Описание решения

### Этап 1. Baseline

Один и тот же запрос про подозрительную активность (25 неудачных попыток
входа + успешный вход) отправляется несколько раз без явного указания
temperature/top\_p/max\_tokens — чтобы зафиксировать, как модель ведёт себя
"по умолчанию", прежде чем менять параметры по отдельности.

### Этап 2. System prompt

Один и тот же пользовательский запрос отправляется с тремя разными
system-промптами: нейтральным, требующим краткого структурированного
ответа (риск + действие по пунктам) и требующим явно разделять факты и
предположения. Это сделано именно так, а не с разными user-промптами,
чтобы разница в ответах объяснялась только сменой system-промпта, а не
самим вопросом.

### Этап 3. Temperature

Промпт про названия сервиса повторяется 5 раз на каждое значение
temperature (0.0, 0.3, 0.7, 1.0). Несколько повторов на одно значение
нужны, чтобы отличить случайный разброс ответов от системного эффекта
temperature — одного запроса недостаточно, чтобы сделать вывод.

### Этап 4. Ограничение длины ответа

Один и тот же объясняющий промпт (архитектура RAG) отправляется с тремя
разными `max\_tokens` (80 / 300 / 900), чтобы увидеть, где именно обрезается
ответ и теряется ли из-за этого часть обязательных пунктов объяснения.

### Логирование

Каждый вызов модели оборачивается в `ask\_model`, которая перехватывает
ошибки API (например, неподдерживаемый параметр) и не прерывает весь
эксперимент, а фиксирует ошибку как часть результата — это важно, потому
что часть локальных серверов не поддерживает все параметры OpenAI API, и
такая ошибка сама по себе является результатом исследования.
Каждый результат пишется в двух форматах: **JSONL** с полным текстом
ответа (для детального разбора) и **CSV** с усечённым превью ответа
(удобно открыть в Excel/Google Sheets для сводных таблиц).

## Запуск

Установить зависимости:

```bash
pip install -r requirements.txt
```

Создать `.env` на основе примера:

```bash
cp .env.example .env
```

Запустить LM Studio с нужной моделью, затем запустить весь эксперимент:

```bash
python src/lab02.py
```

Либо запустить только один этап:

```bash
python src/lab02.py --stage 3 --repeats-temperature 5
```

Доступные флаги:

```text
--stage {1,2,3,4,all}       какой этап запустить (по умолчанию all)
--repeats-baseline N         число повторов для этапа 1 (по умолчанию 3)
--repeats-temperature N      число повторов для этапа 3 (по умолчанию 5)
```

### Переменные окружения

```text
LLM\_API\_KEY   # для LM Studio можно оставить значение по умолчанию "lm-studio"
LLM\_BASE\_URL  # адрес локального сервера, по умолчанию http://localhost:1234/v1
LLM\_MODEL     # точное имя модели, загруженной в LM Studio
```

## Вывод

В ходе лабораторной работы на локальной модели google/gemma-4-e4b (LM Studio) экспериментально подтверждено, что параметры генерации не делают модель «умнее», а лишь управляют способом получения ответа. System prompt оказал заметное влияние на структуру и длину ответа: без роли модель писала вдвое медленнее и многословнее (243,99 с), чем с чёткой инструкцией в 5 пунктов (117,46 с), при этом обе версии system prompt с явной структурой (sys_02, sys_03) были воспроизведены моделью почти дословно. Эксперимент с temperature показал ожидаемую закономерность: при t=0 4 из 5 повторов дали идентичный текст, а при t=0,3–1,0 все повторы оказались уникальными, причём при t=1,0 выросла не только текстовая вариативность, но и разброс задержки и объёма ответа (19,8–94,0 с). Эксперимент с ограничением длины дал не совсем ожидаемый, но не менее ценный результат: при max_tokens=80 и max_tokens=900 видимый ответ оказался почти пустым, несмотря на полностью израсходованный лимит токенов - это показывает, что «больше токенов» не гарантирует «больше полезного текста», и такие аномалии нужно фиксировать и разбирать, а не списывать на «модель так работает». Главный практический вывод работы - это не конкретное «оптимальное» значение temperature, а сам навык: поставить контролируемый эксперимент, менять по одному параметру за раз, измерять эффект через воспроизводимые метрики (число уникальных ответов, задержка, соответствие формату) и на основе этих данных, а не интуиции, собрать конфигурацию под конкретный прикладной сценарий - в данном случае для первичного анализа события ИБ.
