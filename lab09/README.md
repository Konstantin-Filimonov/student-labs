# Лабораторная работа №9

## Тема
Повышение качества RAG-системы: разбиение документов, гибридный поиск, переранжирование и оценка качества ответов.

## Цель
Освоить экспериментальную оптимизацию RAG-системы из ЛР8 с раздельной оценкой извлечения информации (Hit@k, Recall@k, MRR) и генерации ответа (корректность, обоснованность, ссылки, отказ), соблюдая воспроизводимость и требования информационной безопасности.

## Бизнес-гипотеза (вариант 1 — Служба ИБ)
Гибридный поиск (dense + TF-IDF через RRF) лучше находит документы по вопросам с точными терминами (SAST, SPF/DKIM/DMARC, CVSS 9.0), чем чисто плотный поиск. Гипотеза проверяется цифрами в `results/summary.csv`; отрицательный результат также допустим.

## Архитектура

```
Вопрос
  │
  ▼
[1-й этап: dense | lexical (TF-IDF) | hybrid (RRF)] ──► N кандидатов (candidate_n = 12)
  │                      ▲ ACL-фильтр по access_group до ранжирования
  ▼
[2-й этап: reranker (feature | cross-encoder)] ──► top-k фрагментов
  │
  ▼
[build_context: [S1], [S2], ...] ──► LLM (Qwen2.5-3B-Instruct, LM Studio, промпт v1 из ЛР8)
  │
  ▼
Ответ + ссылки ──► ручная оценка (answer_review.csv)

Метрики поиска (evaluate.py) и метрики генерации (answers.py) считаются раздельно.
```

## Задачи
1. Воспроизвести базовую конфигурацию: chunk 600 / overlap 100 / top-k 4 / dense.
2. Ввести журнал экспериментов (`summary.csv`, `search_runs.jsonl`, `run_meta.json`).
3. Исследовать размер фрагмента (300, 600, 1200 символов).
4. Исследовать перекрытие (0, 100, 200 символов).
5. Исследовать top-k (2, 4, 8) с учётом объёма контекста.
6. Реализовать гибридный поиск (dense + TF-IDF, RRF) и сравнить с dense и lexical.
7. Добавить переранжирование (простой feature-reranker; нейронный cross-encoder — расширенное задание).
8. Оценить генерацию для трёх конфигураций: 10 ответимых + 5 неответимых вопросов, 2 повтора.
9. Построить два графика, разобрать минимум две ошибки, сформулировать вывод.
10. Описать мини-модель угроз и реализованные меры защиты.

## Используемые технологии
- Python 3.10+ (в ЛР7–8 использовался 3.14)
- sentence-transformers 5.x — модель `paraphrase-multilingual-MiniLM-L12-v2` (384 dim, CPU)
- scikit-learn (TF-IDF), numpy, pandas, pyyaml, matplotlib
- LM Studio — локальная LLM `qwen2.5-3b-instruct`, клиент `openai`

## Запуск

1. **Окружение** (PyCharm: интерпретатор — `.venv` проекта; папку `src` пометить как *Sources Root*, рабочая директория запуска — корень проекта):
   ```bash
   python -m venv .venv
   .\.venv\Scripts\Activate.ps1
   pip install -r requirements.txt
   ```
2. **Скопировать `.env.example` в `.env`** (нужен только для `answers.py`; `.env` не коммитится).
3. **Проверка данных и статистика фрагментов** (без моделей):
   ```bash
   py src/ingest.py
   ```
4. **Эксперименты по поиску** (все конфигурации из `config.yaml`):
   ```bash
   py src/evaluate.py
   ```
5. **Разбор ошибок** (по умолчанию базовая конфигурация):
   ```bash
   py src/errors.py --limit 2
   ```
6. **Генерация ответов** (запустить LM Studio и модель `qwen2.5-3b-instruct`; три конфигурации выбираются по итогам шага 4):
   ```bash
   py src/answers.py --experiments base_dense_600_100_k4 hybrid_600_100_k4 topk_2_dense --repeats 2
   ```
   Затем вручную заполнить колонки `correctness_0_2`, `grounded_yes_no`, `citation_ok_yes_no`, `refusal_ok_yes_no` в `results/answer_review.csv` и выполнить:
   ```bash
   py src/summarize_review.py
   ```
7. **Графики:**
   ```bash
   py src/plots.py
   ```
8. **Тесты:**
   ```bash
   py -m unittest discover -s tests
   ```

Нейронный reranker (расширенное задание): указать `reranker_model` в `config/config.yaml` (многоязычная cross-encoder-модель, версия фиксируется в отчёте) — эксперимент `rerank_cross_dense_600_n12_k4` тогда выполнится автоматически.

## Формат данных

### `data/corpus.jsonl`
| Поле | Описание |
|---|---|
| `doc_id` | Устойчивый идентификатор документа (по нему считаются метрики) |
| `title` | Название документа (используется как `source` в контексте) |
| `category` | Тематическая категория |
| `access_group` | Группа доступа: public / devs / soc / admins |
| `origin_ids` | Идентификаторы коротких документов ЛР8, вошедших в этот документ |
| `text` | Текст документа |

Корпус ЛР8 состоит из очень коротких записей (90–150 символов), на которых размер фрагмента 300/600/1200 не влияет на результат. Поэтому 40 пунктов ЛР8 сгруппированы в 10 тематических документов по аналогии с `long_corpus.jsonl` из ЛР7; в текст добавлены нейтральные пояснения без новых фактов по темам неответимых вопросов. Все данные синтетические, реальных персональных данных и секретов нет.

Распределение по группам: public — 7 документов, devs — 1, soc — 1, admins — 1.

### `data/questions.jsonl`
| Поле | Описание |
|---|---|
| `id` | Идентификатор вопроса |
| `question` | Текст вопроса |
| `answerable` | true / false |
| `gold_doc_ids` | Эталонные документы (для неответимых — пусто) |
| `expected_facts` | Проверяемые факты для ручной оценки |
| `type` | direct / fact / semantic / technical / lexical / no_answer |

23 вопроса: 16 ответимых (q01–q10, q16–q21) и 7 неответимых (q11–q15, q22, q23). Вопросы q01–q15 перенесены из ЛР8 с пересчётом эталонов на `doc_id` новых документов; q16–q23 добавлены (в т. ч. три «лексических» вопроса и два неответимых вопроса близкой тематики).

### Разбор ошибок
`results/error_cases.md`: (1) q19 — граница фрагмента отрезала условие «после трёх попыток» (ошибка разбиения, при k=2 — ошибка поиска); (2) q20 при chunk 1200 — «размытый» эмбеддинг крупного фрагмента; ошибки генерации — искажение «завершить → приостановить», выдуманная расшифровка DMARC, ответы без ссылок, китайские символы в отказе.

### Вывод
- **Гипотеза о преимуществе гибридного поиска подтверждается слабо.** Hybrid (MRR 0.969) чуть лучше dense (0.958), но не лучше чисто лексического (1.000); Hit@4 у всех трёх равен 1.0. Разница — один вопрос из 16, статистически не значима. Гибрид лучше всего проявил бы себя при ошибках лексического или плотного поиска, но на этом небольшом корпусе их почти нет. Отрицательный результат допустим по условию.
- **Размер фрагмента:** 1200 символов хуже всего (Hit@4 0.875, MRR 0.781, контекст 3499); 300 и 600 по Hit@4 равны, 600 по MRR немного лучше.
- **Перекрытие:** 0/100/200 почти не различаются (MRR 0.958–0.969).
- **top-k:** k=2 даёт то же качество ответов при вдвое меньшем контексте и времени генерации (1121 против 2169 символов, 1.09 против 2.59 с), но один ответимый вопрос теряется на этапе поиска (Hit 0.938). k=8 ничего не добавляет к k=4 при удвоенном контексте.
- **Переранжирование:** простой feature-reranker не помог (MRR 0.927 против 0.958/0.969), Hit@12 первого этапа = 1.0, так что резерва для второго этапа в этих данных не было.
- **Компромиссная конфигурация:** chunk 600 / overlap 100 / k=4, dense или hybrid; при ограничении на длину контекста — k=2.
- **Корректность ответов** у всех трёх конфигураций 1.7–1.8 из 2, различия на уровне одного-двух ответов. Основные потери — ошибочные отказы по q19 и искажения мелкой модели.

## Информационная безопасность
- **ACL:** фильтрация по `access_group` выполняется до ранжирования и передачи фрагментов в LLM (`retrieve.py`, параметр `--user-group`); покрыто тестами. Основная серия запускается без фильтра для сопоставимости с ЛР8.
- **Prompt injection:** найденные фрагменты передаются в блоке `CONTEXT`, системная инструкция запрещает использовать сведения вне контекста. Корпус не содержит инструкций для модели; adversarial-тест — дополнительное задание.
- **Секреты:** параметры LM Studio — в `.env` (в `.gitignore`), в репозиторий попадает только `.env.example`.
- **Логи:** `search_runs.jsonl` хранит ID фрагментов и оценки без текста; полные тексты контекста есть только в `answer_runs.jsonl` (корпус синтетический). При работе с реальными документами такие журналы публиковать нельзя.
- **Внешние API:** не используются; эмбеддинги и LLM работают локально.

## Ограничения
- Разбиение по символам режет текст посередине слова и предложения (алгоритм из методических указаний); из-за этого фрагмент `r01_1` потерял условие и вопрос q19 остался без ответа. Метрика по `doc_id` такие случаи засчитывает как попадание.
- Ручная оценка ответов выполнена по тексту контекста и должна быть проверена автором перед защитой.
- Малый синтетический корпус (10 документов, 23 вопроса): различия в 1–2 вопроса статистически не значимы, выводы относятся только к контрольному набору.
- Размер контекста измеряется в символах; токены не считались.
- Feature-reranker — простой учебный второй этап, не нейросеть; его вес-параметры заданы в `config.yaml`.
- Оценка генерации ручная; LLM нестабильна, поэтому выполняется минимум два повтора.
- Корпус и разметка сформированы под учебную задачу и не отражают промышленную эксплуатацию.
