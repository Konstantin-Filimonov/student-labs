# Разбор ошибок (ЛР9)

Источники: `search_runs.jsonl` (поиск), `answer_runs.jsonl` и `answer_review.csv` (генерация). Корпус синтетический, выводы относятся только к нему.

## Ошибка 1. q19 «Что происходит после трёх неудачных попыток входа?» — ошибка разбиения на фрагменты (base и hybrid), ошибка поиска (top-k = 2)

- Эталон: r01, п. 2.1 — «После трёх неудачных попыток входа учётная запись автоматически блокируется на 30 минут. Разблокировка выполняется администратором».
- Базовая конфигурация (dense, 600/100, k=4): эталонный документ найден (Hit = 1), но только на 3-м и 4-м местах, RR = 0,33. Первым в контекст попал `r04_1` (резервное копирование).
- Фрагмент `r01_1` с фактом о блокировке начинается с середины слова: «апись автоматически блокируется на 30 минут…». Условие «после трёх неудачных попыток входа» осталось в `r01_0`, который в контекст не вошёл. Метрика Hit@k по `doc_id` здесь засчитала успех, хотя полезного для ответа условия в контексте нет.
- Ответ LLM во всех шести запусках (3 конфигурации × 2 повтора) — «недостаточно информации», корректность 0. Отказ честный: модель не выдумала факт, но вопрос ответимый.
- При k = 2 (`topk_2_dense`) фрагментов r01 в контексте нет вообще (Hit = 0 для этого вопроса): ошибка поиска.
- Вывод: ошибка лежит в разбиении (граница фрагмента режет предложение, а перекрытия 100 символов не хватило, чтобы сохранить начало), а не в LLM. Что попробовать: увеличить overlap до 200 символов (в `summary.csv` он не ухудшил метрики), резать по границам предложений/пунктов, а не по числу символов, считать метрику по наличию ожидаемого факта во фрагменте, а не только по `doc_id`.

## Ошибка 2. q20 «Что обязательно проверяется перед выпуском релиза?» — ошибка поиска при крупных фрагментах (chunk_1200)

- Эталон: r08 (п. 5.1: SAST и проверка секретов). При chunk = 1200 символов Hit@4 для вопроса = 0, RR = 0. В топ-4 попали r10_0, r01_1, r02_1, r04_0 — документы без факта о релизе. Тот же эффект у q21 (временный доступ); отсюда Hit@4 = 0,875 против 1,0 у размеров 300 и 600.
- Причина: фрагмент в 1200 символов смешивает несколько тем (в r08 — инъекции, секреты, зависимости, релиз), и его эмбеддинг «размывается»; близкие по смыслу общие фрагменты других регламентов получают более высокий косинус, чем нужный. При 600 символов тот же вопрос находится (в `base` и `hybrid` ответ верный).
- Контекст при этом самый большой (3499 символов в среднем) — крупные фрагменты хуже по качеству и дороже по длине.
- Вывод: ошибка поиска, управляется размером фрагмента. 600 или 300 символов лучше 1200; гибридный/лексический поиск тоже находит этот вопрос.

## Ошибки генерации (при верном поиске)

1. **Искажение формулировки (base, q01, оба повтора).** В контексте: «принудительно завершить все активные сеансы», ответ: «приостановить все активные сеансы». Корректность 1, обоснованность «нет». Поиск ни при чём: нужный фрагмент был первым.
2. **Выдуманная расшифровка (topk_2, q16, повтор 2).** DMARC расшифрован как «Dkim Policy». В контексте расшифровок нет совсем: модель добавила их из собственных знаний, и одна оказалась неверной. Обоснованность «нет».
3. **Нет ссылок и лишние пояснения (hybrid, q01#2, q06#1–2).** В 3 из 16 содержательных ответов гибрида нет `[S#]` (q01#2, q06#1–2), а в q06 добавлены утверждения, которых нет в контексте («передавать параметры отдельно», «очищать от угроз»). Отсюда «верные ссылки» 77,8 % против 88,9 % и 94,4 %.
4. **Языковой сбой (hybrid и topk_2, q13).** В отказе появились китайские символы. Отказ по смыслу корректный, но формулировка испорчена; это ограничение маленькой модели Qwen2.5-3B.

## Замечание о методе

Ручная разметка `answer_review.csv` выполнена по тексту контекста из `answer_runs.jsonl` (проверялось, содержит ли указанный `[S#]` фрагмент факт). Различия между конфигурациями (1,7 / 1,8 / 1,7 балла) — это один-два ответа из 20, статистически они не значимы.
