# Лабораторная работа №1

## Тема

Тестирование локальной языковой модели через LM Studio: проверка
подключения, прогон набора промптов, замер задержки ответа и оценка
стабильности генерации.

## Цель

Освоить базовый программный цикл взаимодействия с LLM через API и научиться сравнивать несколько моделей на одинаковом наборе заданий по критериям корректности, полноты, следования инструкции, практической полезности и времени ответа.

Задачи

1. Настроить подключение к локальному серверу LM Studio через
OpenAI-совместимый клиент.
2. Проверить, что модель, указанная в конфигурации, действительно доступна
на сервере.
3. Прогнать набор тестовых промптов разных типов и зафиксировать ответы и
задержку каждого запроса.
4. Оценить стабильность ответов модели (повторные запросы с одинаковым
промптом).
5. Подготовить шаблон для ручной оценки качества ответов и свести результаты
в единый отчёт.

## Используемые технологии

* Python 3.x
* библиотека `openai` (OpenAI-совместимый клиент)
* `python-dotenv` для чтения `.env`
* LM Studio — локальный сервер, отдающий модель по OpenAI-совместимому API
(`http://localhost:1234/v1`)

Модель: указывается через переменную окружения `LLM\_MODEL` (берётся из
`.env`, конкретное имя — то, что реально загружено в LM Studio).
Запуск: локальный, через LM Studio.
Температура и другие параметры генерации в этой работе не переопределялись
(используются значения по умолчанию) — их исследование вынесено в ЛР2.

## Описание решения

### Этап 1. Подключение к модели

Для работы с локальной моделью выбран LM Studio, поскольку он поднимает
OpenAI-совместимый REST API поверх локально загруженной модели — это
позволяет использовать стандартный клиент `openai` без переписывания кода
под отдельный формат API. Адрес сервера и имя модели вынесены в `.env`
(`LLM\_BASE\_URL`, `LLM\_MODEL`), чтобы не хардкодить их в коде и иметь
возможность быстро переключаться между моделями.

`main.py` перед отправкой запроса дополнительно запрашивает у сервера
список реально загруженных моделей (`list\_available\_models`) и сверяет его
с именем модели из `.env` — это защищает от типичной ошибки, когда в
конфиге указано одно имя модели, а в LM Studio загружена другая.

### Этап 2. Прогон набора промптов

Промпты вынесены в отдельный файл `prompts.py` и размечены по типу
(`prompt\_type`), чтобы результаты можно было анализировать не только по
отдельным ответам, но и по категориям запросов. `run\_experiment.py`
последовательно отправляет каждый промпт, ловит исключения по каждому
запросу отдельно (а не прерывает весь прогон при одной ошибке) и
дозаписывает результат в `results/experiment\_results.csv` — это позволяет
перезапускать эксперимент по частям и накапливать историю прогонов.

### Этап 3. Оценка стабильности

`bonus\_stability.py` повторяет один и тот же промпт несколько раз, чтобы
увидеть, насколько сильно варьируются ответы модели при одинаковых входных
данных и параметрах по умолчанию.

### Этап 4. Сведение результатов

`summarize.py` агрегирует `experiment\_results.csv` (например, среднюю
задержку, число ошибок), а `make\_scoring\_template.py` готовит таблицу для
ручной оценки качества ответов, поскольку автоматически объективно оценить
"хорошесть" свободного текста сложно — для этого нужна разметка человеком.

## Запуск

Установить зависимости:

```bash
pip install -r requirements.txt
```

Создать `.env` на основе примера и указать реальные значения:

```bash
cp .env.example .env
```

Запустить LM Studio, загрузить нужную модель и включить локальный сервер
(обычно на порту `1234`). Проверить, что нужная модель реально загружена:

```bash
curl http://localhost:1234/v1/models
```

Проверить подключение и получить один тестовый ответ:

```bash
python src/main.py
```

Прогнать полный набор промптов из эксперимента:

```bash
python src/run\_experiment.py
```

Проверить стабильность ответов:

```bash
python src/bonus\_stability.py
```

Свести результаты и получить шаблон для оценки:

```bash
python src/summarize.py
python src/make\_scoring\_template.py
```

### Переменные окружения

```text
LLM\_API\_KEY       # для LM Studio можно оставить значение по умолчанию "lm-studio"
LLM\_BASE\_URL      # адрес локального сервера, по умолчанию http://localhost:1234/v1
LLM\_MODEL         # точное имя модели, загруженной в LM Studio
LLM\_MODEL\_LABEL   # произвольная подпись модели для отчётов (необязательно)
```

## Вывод

В ходе эксперимента сравнивались две локальные LLM: Gemma-4-E4B (4B, Q4_K_M) и DeepSeek-R1-Distill-Qwen-1.5B (1.5B, Q4_K_M), доступные через OpenAI-совместимый сервер LM Studio. По среднему баллу (6.7 из 8) лидирует Gemma, по средней задержке (8.2 с против 130.1 с) — DeepSeek.
Разница в задержке объясняется в первую очередь размером моделей (4B против 1.5B) и уровнем GPU-offload: DeepSeek полностью размещена на GPU (28/28 слоёв), тогда как Gemma использует лишь 18 из ~34 слоёв из-за ограничения VRAM. 
Gemma показала стабильно высокое качество на задачах суммирования, классификации, отладки и логики, но систематически нарушала ограничения по длине ответа и жёсткий формат JSON.
DeepSeek, напротив, хорошо справилась с суммированием и логикой, но провалила генерацию кода (нерабочий метод isspecial()), извлечение сущностей (перепутала ФИО и должность), деловую формулировку и задачу по ИБ (бессвязный текст с китайскими иероглифами).
Для интерактивного помощника, где важна скорость реакции, DeepSeek предпочтительнее, но требует осторожного отбора задач — генерация кода и работа с форматом ей пока не по силам. Для пакетной обработки документов, где важнее качество и допустима задержка в минуты, лучше подходит Gemma. Ни одна из моделей не может быть рекомендована для задач, критичных к строгому формату (JSON-схема, деловой текст) без дополнительного пост-процессинга.
