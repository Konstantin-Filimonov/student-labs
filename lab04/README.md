## Цель

Построить воспроизводимый мини-бенчмарк и сравнить две LLM (или две существенно
различающиеся конфигурации) на задаче **первичной классификации событий информационной
безопасности** (`normal` / `suspicious`) с кратким объяснением решения.

## Выбранный сценарий и критерии

- Сценарий: первичная классификация ИБ-событий (п. 7 методических указаний).
- Положительный класс: `suspicious`.
- **Основная метрика (выбрана до запуска моделей): F1 по классу `suspicious` при приоритете Recall.**
  Пропуск реального инцидента (FN) опаснее ложного срабатывания (FP): FP стоит времени аналитика,
  FN — потенциальной компрометации. Accuracy, Precision, Recall, Format compliance, latency,
  токены и стоимость — вспомогательные.
- Политика разметки: `suspicious` — события, указывающие на вероятную атаку, компрометацию учётной
  записи, утечку или серьёзное нарушение политики ИБ. Необычное событие с подтверждённым объяснением
  (заявка, MFA, согласованные работы) — `normal`. Спорные случаи размечены консервативно (в пользу
  проверки аналитиком); обоснование каждой метки — в колонке `rationale` файла `data/tests.csv`.

## Тестовый набор

`data/tests.csv` — **30 синтетических примеров** (реальные данные не используются, п. 5 методички):

| Уровень | Что проверяет | normal | suspicious |
|---|---|---|---|
| `easy` (10) | типовые случаи | 5 | 5 |
| `medium` (10) | нужен контекст (заявка, MFA, известные адреса) | 5 | 5 |
| `hard` (10) | граничные и неоднозначные случаи | 5 | 5 |

Классы сбалансированы (15/15). Текст промпта не содержит примеров из набора; набор после запуска
не изменялся (контроль — `tests_sha256` в `config.json` запуска).

## Запуск

```bash
cd lab04

pip install -r requirements.txt
cp .env.example .env                                   # и заполнить MODEL_A, MODEL_B, MODEL_JUDGE
```

Подготовка LM Studio: вкладка Developer → *Start Server*; имена моделей взять из `GET /v1/models`.
Судья должен отличаться от оцениваемых моделей. Модели опрашиваются последовательно
(сначала все запросы A, затем B), перед каждой моделью выполняется прогревочный запрос, не входящий
в статистику, — так время загрузки модели не попадает в latency.

Проверка конвейера без моделей: `python src/pipeline.py --mock` (результаты имитации в отчёт не
включать — папка запуска помечается суффиксом `_mock`).

Этапы можно запускать отдельно: `--stage run|repeats|judge|metrics|report`, `--run-id <папка>`,
`--force` (перезаписать результаты этапа).

## Ход решения

1. **Подготовка.** Зафиксированы модели, промпт (`v1.0`), параметры генерации (одинаковые для обеих
   моделей), тестовый набор и основная метрика.
2. **Прогон.** Каждая модель обрабатывает все 30 примеров. Сохраняются сырой ответ, время, usage и
   результат валидации. Некорректные ответы получают `predicted = parse_error` и **не исключаются**.
3. **Валидация формата.** Ответ корректен, если это JSON-объект с `label ∈ {normal, suspicious}`,
   `confidence ∈ [0, 1]` и непустым `reason`. Блоки `<think>…</think>` и обрамляющие Markdown-
   ограждения срезаются до разбора; текст вокруг JSON — нарушение формата.
4. **Метрики.** Accuracy считается по всем N (parse_error = ошибка). FN включает parse_error на
   примерах `suspicious`; parse_error на `normal` не засчитывается как TN (иначе сломанный формат
   «улучшал» бы метрики). Дополнительно: bootstrap 95 % ДИ для Accuracy и F1, точность по уровням
   сложности, число уверенных (conf ≥ 0.8) ошибок.
5. **Ручная оценка и галлюцинации.** 10 ответов на модель (одни и те же id для A и B, стратифицированная
   выборка 3/3/4 по easy/medium/hard, фиксированный seed — выбор не зависит от ответов). Рубрика 0–2:
   correctness, completeness, instruction, relevance; отдельно флаг «галлюцинация» (есть существенное
   утверждение, которого нет в описании события и которое из него нельзя вывести). Correctness
   оценивает фактическую подкреплённость объяснения, а верность метки измеряется Accuracy.
6. **Latency и стоимость.** Среднее, медиана, p95; входные/выходные токены из `usage`; стоимость —
   только при заданных тарифах (с датой и источником), иначе не рассчитывается.
7. **Повторные прогоны.** 5 самых сложных примеров × 3 дополнительных запуска на модель. «Сложность»
   определяется правилом (больше суммарных ошибок обеих моделей → ниже средняя уверенность → меньший id).
   Оцениваются смена класса, нарушения формата, разброс confidence, сходство объяснений и разброс
   оценки судьи.
8. **LLM-as-a-Judge.** Независимая модель оценивает те же ответы по той же рубрике
   (`judge_scores.csv`); сравнение с ручной оценкой: точное совпадение, MAE, смещение, ранговая
   корреляция Спирмена, совпадение флага галлюцинации. Ручная таблица заполняется **до** просмотра
   оценок судьи.

## Воспроизводимость и безопасность

- В `config.json` каждого запуска: версия промпта, тексты промптов, модели, параметры, дата,
  sha256 тестового набора. Изменили промпт — увеличьте `PROMPT_VERSION` в `src/prompts.py`.
- Реальные ключи хранятся только в локальном `.env` (в репозитории — `.env.example`). Ключи не
  попадают в `config.json` и отчёты. Все данные тестового набора синтетические.

## Выводы

**Основная метрика** — F1 по классу `suspicious` с приоритетом Recall (зафиксирована до запуска):
в ИБ-сценарии пропуск инцидента (FN) опаснее ложной тревоги (FP). По ней модель A (0.897) уверенно
превосходит модель B (0.800).

**Типы ошибок.** Обе модели одинаково (0.80) ошибаются на `easy` — короткие, малоинформативные
описания провоцируют у обеих излишнюю тревожность (пример id 1 — одна опечатка входа классифицирована
как suspicious). На `hard` модель A безошибочна (1.00), модель B деградирует сильнее всего (0.70):
ей сложнее взвешивать несколько противоречивых признаков одновременно.

**FP vs FN.** FN опаснее для сценария. У A — 2 FN (один из них parse_error), у B — 3 содержательных
уверенных FN (confidence 0.80–0.90), включая опасный случай id 30 (признаки захвата учётной записи
генерального директора переинтерпретированы моделью B как «обычная мера безопасности»).

**Компромисс качество/скорость/стоимость.** Компромисса не возникло: модель A одновременно точнее
и быстрее (latency 1.41 c против 1.66 c). Стоимость не считалась — локальный запуск без тарифа.
Единственный плюс B — компактность (3B против 7B параметров).

**Формат.** B — 100% format compliance. A — 96.7% (1 parse_error из 30), причём на этом же примере
(id 20) нарушение воспроизвелось в 3 из 4 повторных прогонов — системная проблема генерации на
длинных многофакторных описаниях, а не случайность.

**Уверенные ошибки.** У A — 2 из 3 ошибок уверенные (conf ≥ 0.8), у B — 5 из 6. Доля уверенных
ошибок у B заметно выше.

**Согласие с LLM-as-a-Judge.** Умеренное: 75% точных совпадений суммарного балла, 93.8% — с
расхождением ≤ 1 балл, корреляция Спирмена 0.39. Судья систематически завышает Completeness
(смещение +0.31) и сам имеет высокую долю (21.7%) нарушений формата — на выборке модели B он
не смог оценить 4 ответа из 10. LLM-as-a-Judge полезен для масштабирования, но не заменяет ручную
проверку, особенно при небольшой judge-модели.

**Рекомендация.** Для пилота — модель A: выше Accuracy/Precision/Recall/F1 по всем разрезам, ниже
latency, безошибочна на сложных примерах. Нужен retry-механизм на `parse_error` (воспроизводимый
сбой на id 20). Модель B оправдана только при жёстких ограничениях по памяти, с дополнительной
калибровкой уверенности и усиленным контролем FN на сложных примерах.

## Ограничения исследования

Небольшой синтетический набор (30 примеров): доверительные интервалы широкие, различия в 1–2 примера
статистически не значимы. Разметка граничных случаев отражает выбранную политику и может оспариваться.
Оценка ручная (один эксперт) и судьёй — оба источника несовершенны.
