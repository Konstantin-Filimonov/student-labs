# Лабораторная работа №10

## Тема
Подключение внешних инструментов к LLM: Tool Calling (Function Calling), проверка аргументов и безопасная интеграция с поиском из ЛР9.

## Цель
Освоить протокол Tool Calling и реализовать минимальный безопасный слой выполнения инструментов: модель только **предлагает** вызов функции, а проверку и выполнение делает приложение (белый список, права роли, строгая валидация аргументов, лимит вызовов, журнал).

## Сценарий
Вымышленный «учебный SOC-помощник»: реестр инцидентов INC-101/102, оповещения ALR-201…203, условные оценки IP из документационных сетей (203.0.113.0/24, 192.0.2.0/24, 198.51.100.0/24) и база знаний. Все данные синтетические.

## Архитектура

```
Пользователь (роль: soc | public)
  │ вопрос
  ▼
[LLM] ── предлагает tool_calls (имя + JSON-аргументы)         ← недоверенный вход
  │
  ▼
[Диспетчер dispatch(name, raw_arguments, session)]            ← граница доверия
  1. имя ∈ REGISTRY?                     нет → forbidden_tool
  2. инструмент разрешён роли?           нет → permission_denied
  3. JSON, точный набор полей, тип,
     значение (regex / ipaddress)        нет → invalid_arguments
  4. не более 3 исполняемых вызовов      сверх → limit_exceeded
  5. выполнение read-only функции        сбой → internal_error
  │ {"data": ...} / {"error": ...}
  ▼
[role="tool" + tool_call_id] ──► [LLM, tool_choice="none"] ──► итоговый ответ
                                      (новые вызовы запрещены, это не агентный цикл — ЛР11)

search_knowledge_base ──► поиск из ЛР9 (hybrid, RRF, ACL по access_group)
```

## Задачи
1. Проверить модель без инструментов и поддержку tools (`check_model.py`).
2. Описать три инструмента и JSON Schema с `additionalProperties: false`; добавить четвёртый (индивидуальное задание).
3. Реализовать `REGISTRY` и `dispatch` с кодами ошибок `forbidden_tool`, `invalid_arguments`, `not_found`.
4. Реализовать обмен `tool_calls` / `role="tool"` с `tool_call_id` и фазой итогового ответа.
5. Подключить вместо учебного поиска поиск из ЛР9 с тем же интерфейсом (`id`, `text`).
6. Провести отрицательные тесты без LLM и сценарии T1–T13 в двух режимах: (а) без инструментов, (б) с инструментами, по 3 повтора.
7. Посчитать метрики: Tool Selection Accuracy, Argument Validity Rate, Unsafe Call Rejection, Task Completion Rate, Latency.
8. Описать угрозы, меры и ограничения.

## Как работает и почему так
**Зачем отдельный диспетчер.** Ответ модели — недоверенный вход: JSON может быть неполным, содержать лишние поля, чужое имя функции или значение, подобранное атакующим. Диспетчер — единственное место, где выполняется код, и он не зависит ни от качества промпта, ни от JSON Schema.

**Что делает схема инструмента.** JSON Schema подсказывает модели формат вызова (`required`, `additionalProperties: false`), но не защищает: модель вправе её нарушить. Поэтому схемы **генерируются из `REGISTRY`** (расхождение невозможно), а те же правила повторно проверяются на сервере. Модель видит только инструменты своей роли.

**Ограничения.**
- только чтение: инструментов записи/удаления/рассылки/выполнения команд нет; `eval`/`exec`/`getattr` не используются;
- не более 3 исполняемых вызовов на обращение; на лишние `tool_call_id` всё равно возвращается `limit_exceeded` (требование протокола);
- одна фаза выбора и одна фаза ответа: `tool_choice="none"`, новые вызовы игнорируются;
- аргументы ≤ 2000 символов, запрос поиска ≤ 180 символов без управляющих символов, результат ≤ 4000 символов;
- ID проверяются `fullmatch` с ASCII-цифрами (`\d` принимает и «١٢٣», `$` — перевод строки).

## Инструменты
| Инструмент | Вход | Результат |
|---|---|---|
| `get_incident` | `incident_id` (INC-101) | уровень, IP, событие; `{"error":"not_found"}` внутри `data` |
| `lookup_ip` | `ip` (IPv4/IPv6) | учебная оценка риска |
| `search_knowledge_base` | `query` (1–180 симв.) | фрагменты `id`, `doc_id`, `source`, `text` |
| `get_alert` *(инд. задание)* | `alert_id` (ALR-201) | сведения об учебном оповещении |

Роли проверяются на сервере: `soc` — все инструменты и документы `public + soc`; `public` — только поиск по документам `public`.

## Интеграция с ЛР9
`Lab09KB` загружает корпус и конфигурацию из `lab09`, строит индекс по конфигурации `hybrid_600_100_k4` (dense + TF-IDF через RRF, `config.yaml → kb.lab09_experiment`) и применяет ACL ЛР9 по `access_group` роли пользователя. Интерфейс функции не меняется: результат содержит ID источника и текст фрагмента. Модель обязана ссылаться на ID; наличие ID в ответе проверяет сценарий T3.

## Информационная безопасность

| Угроза | Мера |
|---|---|
| Избыточные полномочия | только read-only инструменты; роль проверяется на сервере; модель видит лишь разрешённые ей схемы |
| Подмена имени функции | белый список `REGISTRY`; точное совпадение имени; прямое исполнение по имени невозможно |
| Некорректные параметры | точный набор полей, тип, regex/`ipaddress`, длины; `invalid_arguments` без падения |
| Prompt injection в документах и ответах инструментов | результаты передаются как данные (`role="tool"`), системная инструкция запрещает исполнять их команды; новые вызовы в фазе ответа не исполняются; тест T9 с канарейкой |
| Утечка данных | ACL по `access_group` до ранжирования; журнал без ключей; при реальных данных журналы публиковать нельзя |
| Неограниченное число вызовов / DoS | лимит 3 исполняемых вызова, таймаут клиента, ограничение размера аргументов и результата |

**Что проверяется на уровне модели, а что — приложения.** Модель (промпт, схема) лишь повышает вероятность правильного вызова и вежливого отказа; гарантий она не даёт. Приложение (диспетчер, роли, лимиты) выполняет обязательные проверки независимо от того, что вернула модель, — поэтому первое не заменяет второе.

**Остающиеся риски.** Инъекция всё ещё может повлиять на *текст* ответа (поэтому T9 измеряет утечку канарейки); read-only доступ тоже раскрывает данные (нужны ACL и аудит); при подключении реальных CRM/SIEM потребуются авторизация пользователя, аудит и подтверждение опасных действий.

## Ограничения
- Модель 3B может не поддерживать tools так же надёжно, как крупные модели; результаты относятся к одной модели и конфигурации. Проверьте `check_model.py`, при необходимости смените модель.
- Автопроверка итога опирается на ключевые слова; сценарии с отказом (T6) и «факт/рекомендация» (T8) полезно просмотреть вручную по `scenario_runs.jsonl`.
- Набор из 13 сценариев мал; три повтора не дают статистической значимости.
- Режим (а) не имеет инструментов, поэтому Tool Selection и Argument Validity для него не применимы.
- Корпус KB — синтетический из ЛР9 плюс один «отравленный» документ для теста.
