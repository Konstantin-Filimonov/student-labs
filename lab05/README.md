# Лабораторная работа №5

## Тема
Развёртывание и исследование локальной большой языковой модели.

## Цель
Развернуть LLM на своём компьютере, подключить к ней Python-клиент через HTTP API, измерить скорость
и потребление ресурсов, а затем на измерениях (а не на впечатлении) решить, для каких задач такая
модель годится, а для каких нет.

## Задачи
1. Выбрать и загрузить компактную инструкционную модель, зафиксировать её параметры.
2. Провести диалог из пяти типов запросов и оценить корректность ответов.
3. Реализовать Python-клиент к локальному API.
4. Замерить время ответа и скорость генерации (первый запуск отдельно от повторных).
5. Измерить CPU, RAM, GPU и VRAM до загрузки, после загрузки и во время генерации.
6. Исследовать влияние температуры.
7. Реализовать индивидуальное задание: локальный анализатор журналов событий.

## Используемые технологии
- LM Studio (локальный сервер с OpenAI-совместимым и нативным REST API)
- Модель: Qwen2.5-3B-Instruct, GGUF, квантование Q4_K_M
- Среда выполнения: llama.cpp (CUDA 12, avx2)
- Python, `requests`, `psutil`, `matplotlib`
- PyCharm, Git

## Описание решения

### Выбор модели и среды
Выбрана Qwen2.5-3B-Instruct в квантовании Q4_K_M (файл около 2,1 ГБ). Ключевые аргументы:
4-битное квантование уменьшает размер весов примерно в 3-4 раза относительно FP16, поэтому модель
целиком помещается в видеопамять обычной видеокарты и не требует серверного оборудования; класс 3B
оставляет запас памяти под кэш контекста. LM Studio выбрана как среда с готовым локальным API,
разрешённая методичкой наравне с Ollama.

### Клиент
`src/client.py` обращается к нативному эндпоинту `/api/v0/chat/completions`, потому что он возвращает
статистику генерации (токены/с, время до первого токена). Если эндпоинта нет, клиент переключается на
OpenAI-совместимый `/v1/chat/completions` и считает скорость по общему времени (поле `stats_source`
в `results/benchmark.csv` показывает, какой вариант использован).

### Измерения
- Перед замером модель выгружается, поэтому первый запрос включает загрузку в память (холодный старт).
- Ресурсы снимаются фоновым потоком каждые 0,5 с с пометкой фазы: `baseline`, `cold_generation`,
  `idle_after_load`, `generation`. CPU и RAM берутся через `psutil`, GPU и VRAM через `nvidia-smi`.
  Если GPU не найден, в таблице ставится «нет», а не предположение.
- Температура исследуется на трёх значениях (0.0 / 0.8 / 1.5) по три повтора; повторяемость считается
  как среднее попарное сходство ответов по множествам слов (коэффициент Жаккара).

### Индивидуальное задание
Анализатор журналов (`src/log_analyzer.py`) принимает фрагмент журнала, передаёт его локальной модели и
получает JSON со списком находок (severity, category, evidence, reason, recommended_action). Для
устойчивого формата используется JSON Schema на стороне сервера. Локальное размещение здесь оправдано:
журналы содержат внутренние IP-адреса, имена пользователей и хостов, которые не должны уходить во
внешний сервис.

### Безопасность
- API должен слушать только `localhost`; программа проверяет адрес прослушивания и предупреждает,
  если порт доступен из сети.
- В репозитории нет ключей и весов модели; `.env` в `.gitignore`.
- Код, сгенерированный моделью, программой не исполняется.

## Запуск
```bash
pip install -r requirements.txt
```
1. В LM Studio загрузите модель, откройте вкладку Developer, включите загрузку по запросу (JIT) и
   нажмите Start Server (адрес по умолчанию `http://localhost:1234`).
2. Скопируйте `.env.example` в `.env` и при необходимости поправьте `MODEL_NAME`.
3. Запуск:
```bash
python src/run_all.py
```
Программа попросит выгрузить модель перед замером. Все результаты сохраняются в `results/`,
сводка для отчёта - `results/report_data.md`. Отдельные части: `python src/client.py "вопрос"`,
`python src/log_analyzer.py [файл]`.
