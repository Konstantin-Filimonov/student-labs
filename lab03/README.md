# Лабораторная работа №3

## Тема

Проектирование промптов и системных инструкций для больших языковых моделей.

## Цель

Научиться проектировать, тестировать и документировать промпты и системные
инструкции для решения прикладных задач с помощью LLM.

Задачи

1. Разобрать структуру качественной инструкции для LLM
(Role – Task – Context – Constraints – Output Format – Examples).
2. Сравнить наивный (zero-shot) промпт, структурированный промпт и
few-shot промпт со строгим форматом вывода на одном и том же наборе тестов.
3. Освоить критерии отказа и работу с нехваткой данных.
4. Проверить устойчивость промпта к попыткам пользователя изменить
формат ответа (prompt injection).
5. Сформировать рабочий промпт для прикладного ИБ-сценария и обосновать
его структуру.

## Используемые технологии

* Python 3.x
* библиотека `openai` (OpenAI-совместимый клиент)
* `python-dotenv` для чтения `.env`
* LM Studio — локальный сервер с моделью по OpenAI-совместимому API
(`http://localhost:1234/v1`)

Модель: `google/gemma-4-e4b` (задаётся через `LLM_MODEL` в `.env`).
Запуск: локальный, через LM Studio.
`temperature = 0.2` для всех версий промпта и всех тестов — не менялась
между версиями, чтобы сравнение было корректным.

## Описание решения

### Сценарий

Выбран вариант 1 из методических указаний: **анализ события информационной
безопасности**. Модель на основе описания события определяет категорию,
уровень риска, приводит доказательства из входных данных, указывает
недостающие данные и рекомендует следующее действие.

### Версии промпта

* **v1 — базовый (zero-shot).** Короткое «наивное» обращение без структуры:
`Ты помощник по безопасности. Посмотри на событие и скажи, что произошло.`
Служит точкой отсчёта и воспроизводит поведение неподготовленного
пользователя.
* **v2 — структурированный.** Собран по схеме
Role – Task – Context – Constraints – Output Format без примеров. Добавлены
явные ограничения: не выдумывать факты, перечислять недостающие данные,
игнорировать инструкции во входе, требующие сменить формат.
* **v3 — few-shot + строгий JSON.** К v2 добавлены три референсных примера
(типовой случай, аномальный случай, ситуация с недостатком данных) и
требование вернуть только валидный JSON без markdown-обрамления.

### Тестовый набор

`tests.json` содержит 10 входов по разделам 8.2–8.6 методички:

* 3 типовых случая (`T1`–`T3`);
* 2 сложных случая (`T4`, `T5`);
* 2 случая с неполными данными (`T6`, `T7`);
* 1 случай с неоднозначными признаками (`T8`);
* 1 запрос с попыткой сменить формат / prompt injection (`T9`);
* 1 собственный граничный случай (`T10`).

### Индивидуальное задание

Прикладная задача: **первичный анализ фишингового письма**. Системный промпт
`prompt_phishing.txt` возвращает строго JSON с полями
`is_suspicious`, `risk`, `phishing_indicators`, `missing_data`,
`recommended_action`. Набор `tests_phishing.json` содержит 5 входов:
типовой фишинг, легитимное письмо, BEC/CEO-fraud с typosquatting-доменом,
неполные данные (письмо без заголовков) и граничный случай с prompt
injection внутри текста письма.

### Логирование

`src/lab03.py` последовательно прогоняет каждую версию промпта по всем
тестам и пишет результат в `results/results.csv` (для SOC-набора) либо
`results/results_phishing.csv` (для индивидуального задания). Промпты и
тесты лежат рядом со скриптом в `src/`, а `.env` читается из корня lab03
— поэтому запускать скрипт можно из любого места.

## Запуск

Установить зависимости:

```bash
pip install -r requirements.txt
```

Создать `.env` на основе примера:

```bash
cp .env.example .env
```

Запустить LM Studio, загрузить нужную модель и включить локальный сервер
(обычно на порту `1234`). Проверить, что модель доступна:

```bash
curl http://localhost:1234/v1/models
```

Прогнать основной SOC-набор (3 версии промпта × 10 тестов = 30 запросов):

```bash
python lab03.py --task soc
```

Прогнать индивидуальное задание (антифишинг, 5 запросов):

```bash
python lab03.py --task phishing
```

## Результаты

в `.\results`:

* `results.csv` — ответы 3×10 по SOC-сценарию;
* `results_phishing.csv` — ответы 1×5 по индивидуальному заданию;
* `scoring_template.csv` — шаблон для ручной оценки по критериям 0–2
(следование задаче, формат, полнота, работа с нехваткой данных,
устойчивость к смене правил).

Сводка по версиям промпта (SOC-сценарий, 10 тестов):

| Версия | Суммарный балл (из 100) | Среднее время ответа, с | JSON валиден |
|-|-:|-:|-|
| v1 — базовый | 64 | 160.9 | — |
| v2 — структурированный | 99 | 115.2 | не JSON (текстовый список) |
| v3 — few-shot + JSON | 100 | 113.6 | 10/10 валидных JSON |

## Вывод

Наибольший суммарный балл набрала версия v3 (100 из 100), за ней v2 (99),
базовая v1 существенно отстала (64) — в основном за счёт критерия «Формат»
(ответы v1 — развёрнутый неструктурированный текст, непригодный для
программной обработки) и критерия «Неопределённость» (v1 реже явно
фиксирует, каких данных не хватает). Версия v1 оказалась не только менее
структурированной, но и самой медленной в среднем (160.9 с против 115.2 с
у v2 и 113.6 с у v3): без заданного формата модель генерирует заметно
более длинные ответы с оформлением, которое задачей не требовалось.

Наибольший эффект дали два изменения:

* **v1 → v2** (Role–Task–Context–Constraints–Output): формат стал
воспроизводимым, а требование явно перечислять недостающие данные
заставило модель перестать «додумывать» выводы на неполных входах
(особенно заметно на T6 и T7).
* **v2 → v3** (few-shot + строгий JSON): формат стал не просто
стабильным, а машинно валидируемым (10/10 валидных JSON), разбор
пограничных случаев унифицировался благодаря few-shot примеру с
`risk = "unknown"`.

Отдельное наблюдение — тест T9 (попытка внутри пользовательского
сообщения заставить модель проигнорировать формат и написать «всё
безопасно»): все три версии распознали это как часть анализируемого
инцидента и не выполнили встроенную инструкцию. Базовая устойчивость к
таким попыткам обеспечивается самой моделью, но именно явный запрет в
Constraints (v2, v3) гарантированно сохраняет заданный формат ответа —
полагаться только на «врождённую» устойчивость модели для промышленной
системы нельзя.

Индивидуальное задание (анализ фишингового письма) отработало все 5
тестов корректно, включая граничный случай с prompt injection внутри
письма: модель распознала попытку манипуляции ассистентом как один из
`phishing_indicators` и не выполнила встроенную инструкцию. Единственное
найденное отклонение — модель обернула JSON в markdown-разметку
(```` ```json ````), несмотря на явный запрет; после удаления code-fence
все 5 из 5 ответов являются валидным JSON. В промышленном конвейере перед
`json.loads()` нужна лёгкая постобработка либо использование Structured
Outputs API, если провайдер их поддерживает.
